# One canonical contract

[contract.json](contract.json) is the normative version 1 shape and transition table. [validate.py](../scripts/validate.py) reads it directly (through record.py); there is no donor-specific task schema. The record is optional: tiny work uses none.

A task owns requirements, optional decisions, work units, acceptance criteria, actions, evidence, findings, lessons and documentation references. Record identities bind scope, revision and patch; they are not host permissions. Modes and states are the enums in the table. Read-only investigation/design/review may deliver source-audited findings without claiming implementation or runtime checks.

## Context identities

- `patch_id` is the observed fingerprint: SHA-256 over `estack-fingerprint-v1\n` (a wire identifier kept from before the rename to westack, so existing patch IDs and manifests stay valid) followed by sorted lines `<posix path>\0<file sha256>\n` for the files under `fingerprint.paths` (default: the allowed paths). It may be wider than the write paths, so tests and configuration you may not edit still count. `fingerprint.exclude` lists names (matched at any depth) or relative paths left out; the default is `.git`, `__pycache__`, `.pytest_cache`, `node_modules`, `.venv`, `venv`, `.mypy_cache`, `.tox`, `dist`, `build` and `.next`, and a record may replace it. `.git` and the evidence root are always skipped. Only symlinks and junctions are recorded as `link:<target>` and never followed; other reparse points (cloud placeholders) are hashed. A missing requested path is `missing`. Zero hashed files, or an evidence root that equals or contains an observed path, is an error. `init`, `refresh` and `receipt` store the per-file hashes as `manifests/<patch>.json` in the evidence root (self-verifying: the entries must hash to the name), so a mismatch can list the changed files.
- `revision` is the Git HEAD (40 or 64 hex) read from the nearest `.git` at or above `--repo`, the output of `git rev-parse HEAD`, or a label such as `no-vcs`. A nested folder may keep an explicit `--revision` label; the enclosing HEAD is reported.
- `scope_id` is an author-chosen label for the user's current authority. The checker can only compare it; nothing observes it.
- `author_id` is whoever produced the patch under review or verification.

Staleness follows content and authority: a receipt is current when its `patch_id` and `scope_id` match the record. A moved revision with the same patch (for example after a commit) is reported as a note, not staleness.

## Evidence

Evidence binds a claim to the observed artifact, revision and patch, the operation, environment and raw output digest, with counts, status, negative control and coverage limits. Optional `claim_ids` lets one run back several claims. Files use portable relative slash paths under the selected evidence root; `validate.py receipt` snapshots the artifact and hashes the raw output for you. Types `source` and `review` run no process: both exit fields are null (or both integers). Runtime types need both. A review receipt records that the review ran; defects are findings. A digest cannot prove who ran a command. The root and current context supplied to validation must come from the host/user, not a candidate's untrusted instructions.

`validate.py receipt --patch-before <fingerprint>` (the `fingerprint` taken before the check) writes nothing and voids the receipt if the patch differs when it is written; an unchanged patch is recorded in `limitations`, with the limit that two endpoint samples cannot see a change made and then restored. A run receipt without the flag says so in its notes. No contract field holds it ([verify](../references/verify.md)).

A receipt may be marked `stale` only when its patch or scope differs from the record's, or the check definition it stored changed; it keeps its counts, timestamp and files.

Receipts and acceptance criteria may be `inconclusive`: it ran, but the result can't settle the claim (flaky outcome, missing oracle, environment limitation or ambiguous observation). Never counts as passed; record why and what would settle it. An inconclusive receipt must say so in `limitations`, cannot back a passing criterion or serve as a negative control, and a required inconclusive criterion blocks completion.

Review findings bind author/reviewer context, patch, location, consequence, evidence, severity rationale, correction, adjudication and verification. A finding may also record where the defect entered (`introduced`: `patch`, `affected-elsewhere`, `pre-existing` or `unknown`) and the input or scenario that makes it fail (`trigger`, with its observed or traced result); both are optional. Self-review stays self-review. A review may record its independence `level` from the shared vocabulary (self, fresh-context-same-model, different-model, human); an independent review cannot be `self`, and a required independent review needs a recorded level other than `self`. The helper cannot authenticate reviewer identity.

## History and snapshots

Append history events once with unique IDs. An empty history means state framed; a nonempty history starts at framed; verified or complete records need one. A same-state event (from equals to) is a note and needs a `reason`; `grants` on an event records action kinds the user granted. Build and repair records finish only with a `verified` event after their last `implemented` event. Supplied patch and scope bind every record: a difference fails until the record is refreshed, and final records must supply revision, scope and patch.

With `--previous` (or `--chain` for every numbered version in order), the helper checks append-only history, preserved action outcomes, receipts that change only to `stale`, findings, requirements and decisions that are never removed, adjudication that moves only forward (open → accepted, rejected, deferred or fixed; accepted → deferred or fixed; deferred → fixed), requirements whose text, origin and supersession stay fixed while status moves active ↔ parked or to superseded, and decisions whose question, choice, alternatives, origin, supersession and optional parts stay fixed while status moves forward only.

Finish conditions only get stricter within a scope: acceptance criteria are never removed, and their claim, `required`, `requires_runtime` and `requires_negative_control` never weaken; `independent_review_required` is never dropped; unfinished work units and reviews are never removed; forbidden actions and non-goals are never removed. Relaxing any of these needs a new `scope_id` in the same version plus a history event under that scope with a `reason`. Removing an allowed action kind is a scope change; adding one within a scope needs a new event whose `grants` names it, with a `reason`. Without a prior snapshot the helper cannot detect deletion. Keep numbered snapshots through the host's existing storage; no service is installed.

Reconciliation states are applied/not-applied/uncertain/denied. Inspect uncertain targets before replay; caller observations are not independent proof. An effect observed as applied without an approved decision is reported (`report-unauthorized-effect`). Examples use synthetic identities and cannot authorize real mutations.

Resolving uncertainty against `--previous` requires current passing evidence whose claim is the action ID. For a criterion that requires a negative control, every passing receipt names its own control: a failed receipt for the same claim and scope, with actual failing cases and no skips, of the same type and operation and with the same collected count, on a different artifact. The same collected count is the compatibility rule: both runs selected the same cases, so a crash before collection or a narrower selection cannot stand in. The control may come from an earlier patch, so a red run against the pre-fix file qualifies. Process failure alone is insufficient. Current-scope approved actions still need an allowed action kind after they are applied, and no kind may be both allowed and forbidden. Reintroducing an identical denied occurrence under another ID cannot approve it. Historical applied actions remain retainable after a scope change. Complete records require all recorded work units done; work-unit paths must be portable and inside the allowed paths, and allowed paths must be inside `fingerprint.paths`. Reduce scope explicitly or retain a partial outcome when work remains. Requirement and decision supersession is acyclic.

## Optional fields and the starter

Version 1 accepts optional `decisions[]`, `fingerprint`, `work_units[].acceptance_ids`, `work_units[].rollback`, `evidence[].claim_ids`, `reviews[].level`, `history[].reason`/`grants`, and from westack 1.0 `observations[]`, `acceptance[].verifier`, `resume_check`, `findings[].introduced` and `findings[].trigger`, from 1.0.0-alpha.4 `delegates[]` and `waiting_on`, and from 1.0.0-alpha.5 the fields in the last five bullets. Records without them stay valid, and no gate fails a record for lacking a new field; `tests/fixtures/v1-0.2.0` is a frozen 0.2.0 record the suite checks.

- `observations[]` records what the work ruled out, confirmed or found by surprise. A `ruled-out` or `confirmed` observation cites at least one receipt. Under `--previous` observations are append-only: never removed or rewritten; correct one by adding another that cites it.
- `acceptance[].verifier` is `agent` (the default when absent) or `human`. A human criterion passes only with a passing `review` receipt that backs it and is cited by a completed review at level `human` whose reviewer is not the author. Agent receipts cannot pass it; while open it is reported as awaiting human verification. Within a scope it cannot move from `human` back to `agent`.
- `resume_check` names the required acceptance criterion to re-run first on resume (the cheapest one); it must exist and be required.
- `delegates[]` is the delegation ledger, inside this one record and never a second file: `id` (a plain name, also the name of the worker's private output folder), `parent` (the task id, or the delegate that spawned it), `executor`, `tier`, `scope`, `status`, `continuable` and, once closed, `outcome`. `status` is `running` or an end state (the table lists them). Every end except `finished` gives a `reason`. An entry is open until it has an `outcome`: `landed` with a `ref`, or `discarded` with a `reason`. A record cannot be verified or complete with an open entry. Under `--previous` entries are never removed, their identity is fixed and a closed outcome is never rewritten. The end states say how a delegate ended; evidence results keep the words in the [evidence vocabulary](../references/evidence-vocabulary.md).
- `waiting_on` records what a paused task waits for: `what`, a `check` (`kind` and `target`, plus `sha256` for `hash-matches`), the `next_step` and an `expires_at` timestamp with a timezone. It is a field, not a state: a waiting record keeps its state (usually `blocked` or `partial`) and cannot be verified or complete. `validate.py task` reports it as a note and, given `--repo`, evaluates the two file kinds. A waiting record is not an error, and the helper runs nothing and dispatches nothing.
- Receipts: a blocked, not-run or inconclusive receipt names a `reason` code (timeout and cap-reached add `observed` and `limit`); without one it is tallied as no-reason-given. `definition` hashes the command, expected exit and the files in `paths`; editing one stales the receipt though the patch is identical (`--repo`; `refresh` marks it). `producer` is self-declared, not a signature: a review receipt carries the review's context (an independent review's never the author's).
- Versions: `receipt` and `refresh` write `previous_sha256`, the hash of the version before; `--chain` names the first mismatch and calls hand-copied versions unlinked. It proves continuity, not that the newest version is present or who wrote it. `base_revision`, the HEAD at `init`, is fixed; a handoff must descend from it. Widening `fingerprint.exclude` or narrowing stored `fingerprint.paths` is a relaxation. A `stop` is a field, not a state: it bars verified and complete, and clearing an on-purpose one needs a new scope and a reasoned event.
- Work: a unit's `rollback` is written before its first effect and must be safe if that effect never ran; `checkpoint` names the pre-state. A done unit is never reopened (`retry_of` names the earlier attempt) and, with `acceptance_ids`, reads done only when each passes. A `claim` is the one claimant: an expired lease asks for inspection, not proof the worker stopped, and only an `inspected` unit returns to planned. A delegate's absolute `deadline_at` never moves later; a running one past it reads budget-exhausted.
- Actions, findings: `shown` must contain the target; pending actions are listed as open approvals; a step that newly ends uncertain records a `cause`. A deferred finding's `waived_patch_id` lapses when the patch moves.
- Decisions: status moves forward only; a proposal turns active or rejected through a history event whose `reason` and `resolves` name it, and needs `because` and an `alternative_reasons` entry per alternative. `supersedes` may list several; `relations` are stored once, the reverse view derived. A `confirmation` reads decided but unconfirmed until a passing current receipt names the decision id as its claim or its `acceptance_id` passes. `follow-up` observations need no receipt; `memory-read` lists `entries` that `cites_memory` must name.

The optional `validate.py init` starter creates this same version-1 shape. It requires caller-selected output/evidence scope and observed context (`--repo`, or `--revision` with `--patch`), records `--forbid-action`, `--non-goal`, `--observe-path` and `--exclude` (or `--no-default-excludes`), keys on the task id (a repeat returns the open record, another goal errors naming both, an ended record frees the id), refuses replacement and starts open/unverified with no receipts or action decisions. Supplied allowed actions record an existing scope snapshot; they do not grant permission. JSON records are capped at 8 MiB; evidence digests stream regular files so large artifacts need not be loaded into memory. Package validation rejects symlinks and junctions before directory traversal, strips a leading UTF-8 byte-order mark, and accepts only the front-matter keys name, description, metadata, disable-model-invocation, license, allowed-tools and compatibility (1–500 characters). All path checks remain diagnostic, with no concurrent-filesystem sandbox claim.

The checker supports the contract's deliberately small type/required/enum/range vocabulary. Reject extra keys and malformed JSON. It is not a general JSON Schema implementation, runtime, policy engine or OS boundary. Version changes require explicit migration; do not silently reinterpret old records.
