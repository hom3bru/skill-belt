# Evaluation boundaries and replay

Run `python tests/run.py` from the skill directory. It uses Python's standard library, runs named unittest cases, fails if zero tests are collected, and prints counts. Tests run in disposable temporary directories; no network, models, credentials or donor code are used. The suite exercises package contracts and real synthetic behavior, not model judgment. Frozen expected fixtures live under fixtures; malicious text remains data.

[acceptance-cases.json](acceptance-cases.json) preserves the supplied pilot intent, fixture and oracle summaries; it is an independently serialized implementation mapping, not a byte-identical copy of the parent JSON. [acceptance-results.json](acceptance-results.json) separates deterministic coverage from full-case qualification. E01/E03 require human judgments. E06 requires evaluator independence beyond metadata. E12 requires a real independently configured host denied-path boundary and remains blocked/unsupported. E20 includes only synthetic test-only credential text that no helper consumes.

To qualify a host, independently freeze source/config/tool/model versions, expected labels and oracles outside the candidate write scope. Compare native host, minimal instructions, westack and relevant lawful donor baselines with matched tasks/budgets. Capture actual actions, outputs, revisions, unauthorized attempts, duplicated side effects, unnecessary questions and cost. No new credentials or paid calls are authorized for this release.

For stochastic behavior, predeclare repeated trials, budgets/seeds and held-out tasks. Evaluate activation false positives/negatives using [trigger-cases.json](trigger-cases.json), separately from task quality. Do not call a text or metadata match a model activation result. No universal performance target or statistical superiority is inferred from this pilot.

On 2026-10-27 a coordinator routing check outside this package reported over-triggering on a from-scratch CLI build and on flaky-test debugging, and westack (then called estack) as runner-up for plain bug fixes, CI investigation, PR review and an installation request. The description was narrowed and those requests were added to trigger-cases.json; activation has not been re-measured. `tests/test_hardening.py` holds the 0.3.0 regressions (fingerprint, Git HEAD reading, snapshots, immutability under `--previous`, per-receipt negative controls, optional fields, typed evidence, front matter, CLI and docs agreement, state entry). `tests/test_round2.py` holds the second-review regressions (monotone finish conditions, `--chain`, `receipt`/`refresh`, the stored fingerprint definition and manifests, content-bound staleness, matched controls, stale-receipt rules, review levels, reconcile, front matter, finish path, Git root discovery, the generated field table and the work-unit report), including the reviewer's fooling cases. `tests/test_donor_review.py` holds the donor-review regressions (the `inconclusive` result, the trigger-first description and the adopted module guidance). Each was run red against the earlier code or docs before the change. The description was reordered to lead with its trigger on 2026-10-28; activation is still not re-measured.

The v0.2 continuation also exercised a frozen skill snapshot on two independent authored development tasks: a tiny repair and an interrupted append with a misleading wait acknowledgment. A reviewer-owned oracle was frozen before agent dispatch; its draft newline expectation was corrected before that freeze. These bounded trials are recorded separately in tests/results/usage-trials.json. They have no matched without-skill control, repeated trials, blinded grader or independent host-denied boundary, and do not promote the full E01–E20 protocols to passed.

Further required scenarios include stale receipts, malformed records, uncertain already-applied mutation, adversarial completion replay, changed action approval, forbidden donor instructions, missing dependencies and disconnected call paths. Contract checks do not replace the live audit for egress, persistent policy changes, deployment or credential access.

`tests/test_rename_guard.py` holds the 0.3.1 rename guard: the old name may appear only in the files and wire identifiers it lists, each with its keep rule, and the double prefix of a careless find-and-replace may appear nowhere. It also checks itself against a planted old name in a temporary directory.
