# Verify

Define a falsifiable acceptance condition, then run checks that exercise the changed path. Capture exact command/read operation, environment/tool versions, output file and hash, artifact/revision/patch identity, count, exit and limitations in the Evidence Record.

Before editing, run the repository's relevant test command (the whole suite when practical, even if the task names one file) and keep a baseline receipt that lists the failing tests by name. After the change, rerun the same command and compare failing names: report every failure by name, pre-existing ones included, and keep new failures apart from pre-existing ones. A task's scope limits what you deliver, not what you verify.

Save both raw outputs and compare by name with `python "<core>/scripts/checks.py" diff <baseline> <after>`. It parses unittest, pytest, TAP (node:test) and jest or vitest JSON output, runs nothing, and lists new failures, pre-existing failures, fixed tests, and tests that went missing or became skipped. A failure is pre-existing only if its name and normalised failure text both match the baseline's; the same name failing with different text is changed and unattributed. Exit 0 means zero new failures with nothing missing, 1 means new failures, 2 means it cannot tell (an incomplete or unrecognised run, missing or newly skipped tests, changed failure text); map a deliberate rename with `--rename OLD=NEW`. Keep its JSON with the raw outputs: it is only as true as the outputs it read.
Receipts record tool versions and environment variable names (or whether each is set), never their values. Do not capture `env`, `printenv`, `set -x` or other credential-bearing output in raw output; when output may hold secrets or private data, keep a redacted excerpt unless the user agrees to storing it in full. Redact once, where data leaves (receipts, comments, reports, bundles for another vendor): placeholders for rejected output, no secret-named files, hashes for binaries; heuristic redaction can miss.

Results are passed, failed, inconclusive, blocked or not-run. `inconclusive` means it ran, but the result can't settle the claim (flaky outcome, missing oracle, environment limitation or ambiguous observation). Never counts as passed; record why and what would settle it. A check that ends without a structured result (missing tool, crash, timeout, unparseable output) is a tooling error: record it as blocked, neither failed nor coverage. If the same command finished on the baseline, a crash or timeout on the changed code is failed (a flaky timeout stays blocked or inconclusive) and a harness failure is blocked; neither overwrites an earlier good receipt. Class a failure first: a permanent one stops at once; a transient or intermittent one retries the same command at most twice, and report why it stopped (not retryable, attempts used, a wait past the deadline, no retry policy). Never silently substitute another check; record any substitution and why.

Keep evidence out of the fingerprinted files: use an evidence root outside the repository, or pass it as `--root` so the fingerprint skips it. Write raw outputs there. `validate.py receipt` (see [build](build.md)) records a run: it snapshots the tested file to `snapshots/<sha256><suffix>`, hashes the raw output and binds the record's current patch and scope; `validate.py snapshot <file> --root <evidence-root>` makes a snapshot on its own. Fingerprint the observed paths before every check (`validate.py fingerprint`) and pass the result as `--patch-before`: if the paths differ when the receipt is written, the receipt is void and refused. A read-only inspection records equal fingerprints; two endpoint samples cannot see a change made and then restored, and the receipt says so. A snapshot keeps a red-phase receipt valid after an in-place fix. Reads and reviews (types `source`, `review`) run no process: set both exit fields to null and `executed` to the number of observations. Runtime receipts need both exit fields. Record the operation exactly as run; put where the artifact came from in coverage or limitations, not in the operation.

Separate source audit, unit, contract, integration, end-to-end and host evidence. In the shared vocabulary, source-audited reaches at most present or wired; a passing runtime receipt makes a claim tested; an e2e or host receipt on the real product path makes it observed. A source reading or valid schema cannot become runtime-tested. A successful shell exit with zero executed tests is incomplete. Skipped tests are not passes. Mark unavailable tests not-run or blocked; report flaky/retried results together rather than replacing the failure.

Where the check claims to detect a mechanism, run a frozen broken/removed-path control and show that it is rejected. For a bug fix, the red run before the fix is the control when the check itself has not changed since; otherwise rerun the check against a copy with the fix reverted. For a generated verifier, a constant-true check must fail against the broken copy. A model-written verification script runs under a strict header (stop on error, unset variables, failed pipeline stages; the project supplies the shell form), and lines that switch it off or trap exits are dropped: a check that cannot fail is not a check. Every passing receipt behind a criterion that requires a control names its own failed control: the same claim and scope, the same evidence type and operation, the same collected count (both runs selected the same cases), and a different artifact (a different snapshot hash). Store the raw failing output. Do not let current candidate writes change an independent evaluator's oracle.

Derive expected values independently of the code under test; an expectation computed by that code always agrees with it. Choose each broken copy from realistic mutation kinds: a wrong constant or argument, the wrong branch, a missing side effect or state change, an empty or default return, missing validation. Pair the failing control with a run showing that legitimate behaviour still passes, so the failure is specific to the mechanism. Counts from a process the candidate code controls are self-reported; the control gives them meaning.

An unexpected process exit after all cases passed, a crash before collection or a different selection does not show that the broken mechanism was detected. A failure from another scope or task is not a control.

A removal or security claim is a claim of absence: probe the exact pre-change identifiers on every copy, expecting each probe to fail; a positive answer names the survivor. Rotate an exposed secret before purging history.

Before reusing receipts, compare current patch, scope and observed artifact hashes, plus the recorded check definition (command, marker, rules) and tool version; re-run authorized checks after material change. A new commit with identical content leaves receipts current (the revision change is reported). A receipt may be marked `stale` only once its patch, scope or recorded check definition differs; stale receipts keep their files. Check that the raw output exists and matches its digest. These checks detect stale/missing/contradictory records, not forged evidence.

Validate optional records with [validate.py](../scripts/validate.py) (`task --repo`, as in SKILL.md). It does not execute the recorded command, parse test logs into truth or qualify the host. Assertions supplied by the builder and confidence scores are not independent validation.

Evaluate model behavior separately, by the evaluation protocol (`tests/EVALUATION.md` in the repository). Deterministic fixture checks and bounded usage trials are different evidence; neither shows multi-host effectiveness or benchmark superiority.

## Running code you did not write

Code that is not the user's own (a mined repository, a web fixture, a fetched project's tests) runs only with all of these: no network, an empty environment, a read-only target, writes to scratch only, and limits on time, memory and output. If the host cannot supply one, do not run it; the receipt is blocked and names the missing control. A test command is not read-only (a runner can execute arbitrary code through exec-style flags and hooks), so judge it by what it can start. westack installs no sandbox: the host supplies these controls or the code does not run.

## Broken-copy control in a disposable worktree

When the control must run after the fix, keep the working tree (and its fingerprint) untouched, under existing authority to create a temporary worktree:
1. `git worktree add --detach <temp>/control HEAD`, outside the observed paths and the evidence root. With the fix still uncommitted, HEAD already holds the pre-fix code.
2. Copy in the current versions of any new or changed test files the check needs, then break the mechanism there (revert the fix, or disconnect the call).
3. From `<temp>/control`, run exactly the same command as the passing run, writing the raw output into the evidence root.
4. Record it with `validate.py receipt ... --repo <the real repository> --artifact <temp>/control/<broken file>` and the same `--operation`. It binds to the working tree's patch, and the snapshot keeps the broken file.
5. `git worktree remove <temp>/control` after the receipt is written.

With no saved baseline, the same worktree proves one failure pre-existing: run just that test at the parent commit, with a receipt bound to that commit; never stash, check out or reset the work.

## Applications and harnesses

When the task needs a running UI, service or CLI harness, identify the exact instance/build and who owns its lifetime. A step that changes state names its target explicitly, never one found by scanning ports; its fixture inherits only allowlisted environment variable names, and a credential goes with it only to a loopback URL. Establish that it is usable before interaction. After a failed interaction, recheck the instance rather than reusing an earlier readiness assumption. Exercise the user's path and capture the observable result, not only a successful launch or health check. Before relying on a monitor or API, ask it a question with a known answer; a wrong or missing answer blocks it.

Keep proof outside disposable instance state. Clean up only resources owned by this task under the existing authorization, then confirm that the receipt's files still exist and retain their hashes. If evidence was destroyed during cleanup, leave verification incomplete and recover or rerun the authorized check. No lifecycle daemon or sandbox is supplied.

Control-plane success must be recorded for its actual claim: a request was acknowledged, an observer returned, or validation succeeded. Inspect payload fields such as executed, state and errors before claiming product work or completion. An exit of zero alone cannot establish those outcomes. A check that can degrade records what was asked, available and used; a zero-exit run that never made its model call is blocked.
