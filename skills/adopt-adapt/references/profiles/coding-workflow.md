# Profile: coding workflow

The host is where this run executes; the recipient is the workflow being assessed. One host may assess tooling for another, but compatibility must be demonstrated for the user's actual target environment.

Start through the [generic profile](generic.md). Ask for or inspect only authorized user-supplied context: target host/OS/runtime and exact version, current skill/plugin identity, installation root, instruction precedence, hooks, permission boundaries and rollback. No machine inventory, account, global configuration, shell choice or duplicate-install state is bundled here. Unread settings stay UNKNOWN.

Keep the plans-only contract. Donor setup, installation, hook activation, credential access and global setting changes are separate actions requiring applicable user authorization. A donor's suggested configuration is not active wiring or permission. Persona/profile capture is opt-in; do not move workflow conventions into unrelated application runtime.

Use the tooling rubric: real workflow relevance 0–3, novelty 0–2, platform viability 0–3, surface/reversibility 0–2, one strongest penalty. Ground each component in the named host and current receiving seam; unknown viability is not a passing score.

Apply skill-injection, supply-chain, hook-intake and checker-honesty checks. A valid transfer plan names the exact proposed destination, duplicate-name behavior, load-identity check, required restart and reversible disable/uninstall path, without assuming any one vendor's current precedence semantics. Preserve existing hooks/settings rather than silently replacing them. Evaluate trigger behavior and paired with/without-skill outcomes on authorized held-out prompts; helper tests do not establish host loading or general effectiveness.
