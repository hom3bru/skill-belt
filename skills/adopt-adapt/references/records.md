# Local record and helper contract

RE records require `method`, `output`, `baseline`, `contribution`, `distribution` and `method_checks` on each `ledger.re_claims[]` row. [Method contracts](re-methods.md) defines exact values/check keys; each check is `{status,evidence}`. Split hybrid projects into separate, uniquely identified claims. `other` needs `method_reason`. All passing claims need a discriminating `oracle_kind`, positive executed `run_counts`, a negative control and passing method checks; matching claims need `oracle_kind: exact`. Optional `progress` carries integer numerator/denominator, unit, basis and explicit exclusions. The renderer prints this evidence before the verdict. Older records without this contract must be explicitly re-assessed; do not invent a method or convert historical results into a new pass.

Use Python 3.10+ from the actual host. Run helpers with `python -B` to avoid writing bytecode into the installed bundle. Helpers use only the standard library and never fetch a URL or execute donor code.

## Practical flow

For a bounded manual source review, the skill permits a concise ledger with `machine validation not run`. A helper validation of QUEUED inputs confirms only those inputs; it does not validate narrative completion or change their state. When using full records, store the actual transitions and generate/check the published report from that completed record. Proposed behavior can remain untested without blocking a source-grounded adaptation with an inspected receiving seam and explicit prerequisites.

Choose manual or structured mode before creating files. Manual mode needs no machine record and may finish `READY (manual assessment)`. If a record exists, `python -B "<skill-directory>/scripts/aa.py" status <run-dir>/run.json` reports its actual states and whether it contains any ready records or only inputs; it never certifies a separate narrative. Keep manual completion and saved record state separate, and report only commands actually run. Apply [narrative review](narrative-review.md) before publication.

`init <run-dir> --source <locator> --recipient <stable-id>=<profile>` creates `run.json` and `inputs.json`. Repeat options for several inputs/recipients. IDs `s1...` and `q1...` preserve supplied input order. Source and recipient IDs must be distinct. A bare `<stable-id>` gets profile `unspecified`; no pair for that recipient can be READY until a `routing` row records its chosen profile (for a run with no recipient, a row for `unspecified` with its evidence). Input-only and incomplete runs still validate, so `status` and `handoff` keep working.

**Several mechanisms from one source.** A record carries one decision per source/recipient pair, scored on its best mechanism. To give a second good mechanism its own verdict, value, transfer contract and acceptance test now, register the source again with a fragment naming the mechanism (`--source <locator>#mechanism-<name>`), capture the same bytes for that source ID, and keep each pair's claims about its own mechanism; the map and coverage may repeat. Per-mechanism decisions inside one pair are later work. The input manifest guards accidental source deletion; it is not a tamper-proof external log. Record `request` and actual host name. Keep the fixed host capabilities: renderer validation true, host prevention `unavailable`, detection `exported-report-only`.

Resolve each source's `locator`, `revision` and `kind`. The input locator is preserved in the manifest; put the canonical resolved locator into an additional source field `resolved_locator` rather than replacing the original. Revisions are full commits or explicit captured document identities, never silently substituted HEAD. Kinds are meaningful source types (`repo`, `paper`, `docs`, etc.). Recipient rows contain `id`, `profile`, `revision`, `snapshot`. An unspecified recipient uses profile `unspecified`; no target-specific fit score or ADAPT is permitted. Every recipient with a READY pair needs a `routing` row for its profile, and `score.rubric` must be that profile's rubric: its own `## … Rubric` section where it has one, else `generic` (`tooling` stays an alias of `coding-workflow`).

`snapshot <root> --path <file> ... --output <snapshot.json>` hashes explicitly selected relative files and records absolute root, Git HEAD if available, scope and time. Include relevant rules, callers and feature flags, even when untracked. A missing explicit path is recorded as null so creation is detected. Copy that object to recipient `snapshot` and set `revision` to its `id`. This is intentionally not a full disk scan. Validation rechecks those files and root identity; excluded dependencies remain limits. `--historical` replays an old record without live rechecks and cannot be used to claim present applicability or append a new live history event.

`capture <run-dir> <local-file> --subject <id> --revision <identity>` copies bytes to `artifacts/<sha>.bin` and prints an evidence object. Add it to `evidence`, then change `read_scope` from `unread` to the actual inspected coverage and describe limitations. Capturing is not reading. Evidence objects require `id`, subject, revision, path, sha256, bytes, origin, captured_at, read_scope, limitations. Local receipt bytes are independently checked; remote origin and agent claims are not authenticated by this helper. Keep original acquisition traces when needed. Do not copy sensitive data beyond its authorized audience.

Claims have `id`, `subject`, `text`, `kind`, `status`, `scope`, `limitations`, `evidence` IDs, optional `contradictions` claim IDs and `review`. Kinds: source_observation, mechanism, recipient_opportunity, experiment, verified_outcome. Status: supported, inferred, unvalidated, refuted, stale. **Supported requires read evidence of that exact subject/revision plus a nonempty semantic review.** The checker verifies relationships/bytes; the reviewer must actually check entailment. An agent can write a false review, so validator success is never truth certification. Verified-outcome claims need real observed outcome evidence in their review, not just source code. Every claim also carries `level`, the highest rung of the [evidence vocabulary](evidence-vocabulary.md) actually shown (claimed/present/wired/tested/observed): present and above need read evidence of that subject; tested and observed need `execution` = an eligible run of the same subject captured in this work; a stale or unvalidated claim stays `claimed`; a supported verified_outcome is tested or observed. Legacy claims without a level need re-assessment, not conversion.

Each source/recipient item retains `id`, `source`, `recipient`, `state`, `transitions`. Allowed initial state QUEUED; QUEUED → RESEARCHING/UNPROCESSED/CANCELLED; RESEARCHING → READY/BLOCKED/CANCELLED/UNPROCESSED. BLOCKED/UNPROCESSED/CANCELLED can resume through RESEARCHING; READY can reopen through RESEARCHING. A state change appends to transitions and matches final state. Non-READY items require `reason` and cannot carry `decision`. Save after meaningful progress/interruption; no source vanishes. READY means ready to render, not already published.

## READY item

`ledger` contains:

- `primary`: nonempty read evidence IDs for this source.
- `map`: provider codewiki/deepwiki/self-synthesized/not-applicable; content; evidence IDs; limitations (unknown edges and diagram extraction go here). Self-synthesized from code, releases and independent references is the default; a hosted wiki is a donor-steerable hint, recorded only when used. Repos cannot use not-applicable. Inadequate raw material means BLOCKED, not a fabricated complete map.
- `coverage`: examined names, total integer or null, refutation_targets, blind_spots (empty allowed), overlap_claims IDs, adequate boolean. Explain blind spots, not only names. Each refutation target names the observation that would refute the claim, as a sentence or `{target, outcome: confirmed|refuted|unknown}`; placeholders such as `-` or `n/a` are rejected.
- Optional `coverage.subsystems`: rows with unique `id`, `scope`, `mapped`, `inspected`, `exercised`, `evidence` IDs, `execution` IDs and `limitations`. Each stage is `complete|partial|unknown|not-run|not-applicable`. Inspected rows cite read donor evidence; exercised rows cite captured runs. A partial or unrun provider does not block a narrower ready assessment. Older records without rows remain selected-file coverage; they cannot imply subsystem qualification.
- `salvage`: exactly algorithms/error_handling/data_structures/security_compliance/performance. Each has result found/none/not-applicable, note and nonempty source evidence IDs. Explain why not-applicable; unknown requires incomplete state.
- `gates`: integrity, policy, paid_policy preserved/user-replaced, flags list; a replacement requires authorization text. Each flag has code from judgment, scope whole/mechanism/both, status unresolved/resolved/blocked, resolution. Scope keeps paid whole-tool DISCARD compatible with free mechanical ADAPT.
- `doubt`: depth full/light, against, for, environment, resolution, evidence IDs, unknowns list, consequential boolean, decision_uncertainty boolean. The deterministic route of SKILL.md §7 is checked (full for a transfer result, any salvage `found`, fit 5–7, consequential or uncertain); `aa.py doubt … --salvage-found` computes the same rule.
- Optional `review`, required for ADOPT, a governed/frozen/perimeter `transfer.seam_status`, `doubt.consequential` or `confidence_level: high` (SKILL.md §7): `{level: self|fresh-context-same-model|different-model|human, artifact: <file in the run directory>, sha256, disconfirming, checked}`. The artifact is the packet the reviewer received or its report; the validator hashes it and refuses level `self` wherever review is required.
- `legal`: flag, route, ladder steps, advice notice, sources (http(s) URL and an ISO `accessed` date) and `hard_line_hit` (see [legal](legal.md)). Every reuse route (any route but `discard`, whole tool or part) needs `patent_signal`; idea-only routes also need `terms_restriction` (none/hit-or-present/unknown). GREEN needs the applicable checks `none`, and a patent hit needs `escalate_to_lawyer: true`. A hard line makes the donor and every part RED. Optional `parts[]` rows `{id, part, flag, route, basis}` hold the flag of a transferable part; the decision's `legal_part` names the part a transfer relies on. A whole-tool RED/UNKNOWN then requires `whole_tool: DISCARD`, and the named part's flag gates the transfer. A `discard` route never carries a transfer. An UNKNOWN licence (whole tool or part) becomes YELLOW only with `waiver: {by, covers: licence, text, date}` recording the owner's words.

The validator checks recipient ownership of overlap claims and doubt evidence. Another queued donor can support a comparative argument; another recipient cannot supply this recipient's facts. These checks catch identity mistakes, not semantically unrelated prose attached to correct IDs.

`decision` contains whole_tool and result from the SKILL.md §8 result set, summary, `confidence` (scope/reason text), `confidence_level` (low/medium/high), integer `mechanism_value` 0–3, next_step, claims IDs and recipient_claims IDs (anchors: SKILL.md §4). Legacy text mechanism values are rejected and need re-assessment, not conversion. ADOPT/ADAPT/ADAPT-with-prerequisite need `mechanism_value` ≥ 2; a whole-tool ADOPT also needs a scored fit ≥ 8. Referenced decision claims must be supported/inferred and belong to this pair; at least one supported source fact is required. Explain `contradiction_resolution` when cited claims have contradictions. Recipient-specific ADOPT/ADAPT/ALREADY-COVERED requires supported recipient claims and live snapshot.

Confidence and value are capped by the decisive claims (`claims` plus `recipient_claims`): a CLAIMED-level or inferred decisive claim → `low`; `high` → every decisive claim WIRED or above and at least one TESTED or OBSERVED; value ≥ 2 → a supported source claim at PRESENT or above; value 3 → a decisive TESTED or OBSERVED claim. ALREADY-COVERED has value 0; INCONCLUSIVE is `low` with nonempty `doubt.unknowns`; OPPORTUNITY (result or whole tool) needs an `unspecified` recipient. Optional `promising_check` is allowed only on a DISCARD at value 1 and renders `DISCARD (promising: <check to run>)`.

For such target results, `inventory` has implemented/wired/tested/observed objects, each `state` present/absent/unknown plus `scope` with cited support. Wired, tested or observed `present` requires implemented `present`; tested or observed `present` also needs `run` = the ID of this recipient's eligible execution evidence captured in this work ([evidence vocabulary](evidence-vocabulary.md): author-tested results rank no higher than WIRED, so record them as `unknown` with the CI evidence in `scope`). ALREADY-COVERED requires implementation and wiring present; tests/observation can still be unknown and must be disclosed. This structural check cannot discover an omitted caller for you.

`score` is null with `score_reason`, or `{rubric, components: [four integers in documented order], penalty, total, rationale}`. ADAPT/ADOPT results require `transfer` with behavior, donor_closure, recipient_seam, semantics, alternatives, effects_retry, composition, rollback, authorization text, `relation` (new/replaces/augments/makes-usable; replaces or augments when the inventory shows the capability implemented and wired), `seam_status` (governed/frozen/perimeter/ungoverned, from the recipient's rules for that seam), and verification with donor_parity/domain_correctness/recipient_regression/entry_integration. ADAPT-with-prerequisite also requires prerequisite. Inapplicability/unresolved setup is explicit text, never fabricated passing tests.

## Check and output

```text
python -B "<skill-directory>/scripts/aa.py" validate <run-dir>/run.json
python -B "<skill-directory>/scripts/aa.py" render <run-dir>/run.json --output <run-dir>/report.md
python -B "<skill-directory>/scripts/aa.py" check-output <run-dir>/run.json <run-dir>/report.md
```

Render refuses existing output files and invalid records. It emits the full manifest, then each completed ledger before its result, and visibly incomplete items without results. It escapes source-controlled text so it cannot inject report markers or rows. `check-output` compares a supplied report to deterministic rendering; it catches changed order/missing items/content. It does **not** monitor chat or prevent the agent writing an early verdict elsewhere. Emit the report's ledger before the result in the actual chat, too.

The renderer prints exact shared donor facts once, before every dependent recipient verdict. Different mapping/coverage/salvage variants are retained and name their pairs. Recipient gates, legal route, doubt and transfer conditions remain per pair; compact output is not permission to omit them.

For optional recovery of an interrupted structured run, see [the handoff index](handoff.md). It projects the saved record without changing reports or assessment states.

## Execution evidence

The supported `verified_outcome` claim and any passing RE claim need `execution: <evidence-id>`. The evidence row has `artifact_kind: execution`, the same subject/revision and reviewed `read_scope`. Supported outcomes also include that ID in `evidence`. [execution](execution.md) describes the explicit runner and bounded handoff; normal `aa.py` validation does not execute commands.

The validator checks captured receipt/raw stdout/stderr bytes, recomputes positive-case `run_counts`, passing positive `assertions` and passing `negative_controls`, and compares RE declarations to those results and the captured executable hash. Passing negative-control rows mean the checker rejected a deliberately wrong result, not that the wrong result was accepted. At least one positive check and one control suffice for a narrow outcome. Live validation rechecks declared harness/input/executable identities; historical replay checks the retained bytes without claiming current applicability.

This is a local consistency check, not an authenticated external witness. A reviewer must still decide whether observations support the claim's scope and whether the oracle/control are independent and meaningful. Isolated `check_re_claims(ledger)` tests check shape only; full `validate` binds evidence. Do not fabricate receipts to upgrade legacy records: use `not-run`/`unknown` or reassess with an authorized run. Supported source facts and proposed adaptations need no execution receipt. Failed runs may be recorded as supported experiment observations; they cannot become a passing verified outcome.

After actual publication, `history <run.json> --ledger <configured-jsonl> --published-report <report.md>` appends timestamp, record digest and completed decisions without reading old entries. The command assumes its publication assertion is true; a written file alone does not prove user-visible publication. Repeated calls append repeated events; do not retry blindly after uncertain write completion. Inspect tool outcome/file append receipt without feeding past verdicts into evaluation.

After an accepted plan is implemented, `outcome <run.json> --item <id> --result passed|failed|skipped|blocked|not-run --ledger <outcomes.jsonl> [--receipt <raw-output-file>] [--reason <text>]` appends one line beside the original result, mechanism value, confidence and the plan's `transfer.verification` (passed/failed need the receipt, whose hash is recorded; skipped/blocked/not-run need a reason). It replays the record historically, because the recipient has changed, and refuses a pair with no transfer plan. It executes nothing and never reads earlier lines. The line is calibration data for reviewing this skill, never an input to a fresh judgment (SKILL.md §0.8).

`invalidate <lessons.json> <lesson-id> --output <new-file>` marks that node and all descendants stale. Each lesson has a unique id and parents list; other fields follow lessons.md. Retain original provenance. This graph can identify dependent records, not authenticate their claims.

## Agent-surface, RE and hook ledger fields (checked by aa.py)
- `ledger.donor_risks[]`: `{code, evidence, status, scope}`; codes in [due-diligence](due-diligence.md); evidence must cite `file:line` or a URL. Required when source `kind` is `skill|hook|mcp|agent-config|plugin` (may be `[]` after screening). A `present` risk forces ADAPT-with-prerequisite for live transfer and forbids whole-tool ADOPT when scope is whole/both.
- `ledger.re_claims[]`: `{id, claim, status, scope, reported_as?, provenance{tool,version,sha256,options,label,decompiler?}, assertions, negative_controls, verified, legal_posture}` per [re-verification](re-verification.md). `verified:true` needs status `pass`, ≥1 assertion and ≥1 negative control; `campaign-pass` needs scope `campaign`; `decompiler:true` needs label `inferred`.
- `ledger.hooks[]`: `{id, content_sha256, approved_sha256, approved_by, output_schema, env, approval_log, on_error, event?, max_iterations?, auto_answer?}` per [hook-intake](hook-intake.md).
- `re_claims[]` optional `oracle_kind` (required when `verified`; recompile-only/self-roundtrip/fallback cannot verify) and `run_counts{total,skipped,failed}` + `skip_allowlist[]` (pass needs total>0, failed 0, one reason per skip). New donor-risk codes listed in [due-diligence](due-diligence.md).
- `hooks[]` also needs `files[{path,sha256}]` (script + every loaded file), matching `approved_files{path: sha256}`, a valid regex `matcher` if present, and `decision_log: durable`. Donor-risk codes are listed in due-diligence.md.
