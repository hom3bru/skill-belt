# Routing: which recipient profile applies

Run this before source acquisition. Output a **ROUTING** block before donor work, listing each recipient/profile, confidence and inspected evidence.

## Signals and authority

| Signal | Routing consequence |
| --- | --- |
| User names a recipient or supplies its root/rules | Preserve that scope; inspect its current instructions and use generic until a dedicated user-supplied profile is grounded. |
| Explicit request to review adopt-adapt itself | SELF is eligible; name the exact bundle. A skill donor alone never selects SELF. |
| User targets skills, hooks, plugins or host configuration | Coding-workflow is plausible; inspect the actual named host and settings within authorized access. |
| Repository identity or target path matches inspected recipient context | Record the path and supporting rule, with high confidence. The outer workspace cannot override an explicit recipient root. |
| Donor domain or wording suggests relevance | A discovery hint only; it does not prove recipient identity, a need or current wiring. |
| No recipient is established | Use generic or OPPORTUNITY with no fit score. |

High confidence needs explicit user naming or inspected recipient identity; medium needs relevant supplied context; low means unconfirmed adjacency. Do not infer private project names or controls from the donor's domain. Legacy named profile files are user-context stubs, not automatic discovery rules.

## Decide proportionately

1. Explicit scope wins. For fixture-only work, assess those fixtures and use generic unless their actual project identity is established.
2. Never select SELF without explicit intent. An ordinary run may retain a possible SELF lesson without evaluating or changing the skill.
3. Clarify only consequential ambiguity: conflicting recipient requirements, unclear protected/frozen boundaries, or unclear intent to evaluate SELF. Preserve authority already given; do not turn a low-risk routing choice into a repeated approval request.
4. Low-confidence recipients receive a shared donor ledger and a short fit note, without ADOPT/ADAPT until an actual receiving seam is inspected. Proposed changes may remain unimplemented; claims of wiring/execution need their own evidence.

## Multiple recipients

Build one shared donor ledger per source: identity/pin, coverage, applicable due diligence, injection screen and donor mechanisms. Then assess each recipient independently: snapshot, current rules, fit, doubt, verdict, transfer conditions and acceptance test. Finish with a cross-recipient summary, flagging differences and their actual causes.

Never transfer one recipient's governance, privacy rules, runtime constraints or rubric to another. Cite only the relevant recipient's inspected evidence. The helper checks recipient ownership and shared donor receipts; it cannot establish the truth of profile prose.

Synthetic example: `ROUTING: generic / recipient A (high: user supplied root and instructions) · coding-workflow / named host (medium: configuration target, host settings unread) · self: not selected (no explicit intent)`.

Examples are navigation aids, not authority. A frozen receiving path for one recipient may justify deferral there while another permits a bounded plan; an unapproved paid dependency remains blocked until the user explicitly replaces that policy. Do not silently resolve a genuine product or consent conflict.
