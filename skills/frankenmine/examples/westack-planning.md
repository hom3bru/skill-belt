# westack: a worked example of continued synthesis

westack (then called estack) is a product built with Frankenmine. Mechanisms from several catalogue sources had to become one coherent workflow, with explicit ownership and observable behaviour. westack does not define Frankenmine's product domain, and other projects need not use its modules.

**What happened.**
- **Frankenmine 0.1.2.** Its continuation registered westack's actual twenty-decision manifest. Every unit was queued without importing its claims: eighteen URLs declared full commits and two stayed unpinned.
- **westack 0.2.0.** It was built through a Frankenmine continuation run. That run added a canonical task starter, three bounded raw-source reviews, lifecycle and recovery guidance, and 73 deterministic tests.
- **Limits.** These results are recorded in BUILD_REPORT.md. Two authored developer tasks there passed reviewer-owned product checks, but they are not a controlled test of Frankenmine's effectiveness. Registration is not source qualification, and no catalogue-wide or runtime-effectiveness claim follows.

**A prompt for further work.** For example: "Use Frankenmine to continue westack from its current build. Separate skill content, workflow control, tools, memory and host enforcement. Compare the strongest existing solution and a minimal fresh dispatcher. Inspect raw load-bearing source and rights. Preserve host permissions." Name the baseline build and the authorized output root, and state the behaviour the next slice should improve. See [continuation](../references/continue-synthesis.md).

Ownership decisions a westack-like synthesis has to make:

| Conflict | Ownership decision |
| --- | --- |
| Repeated interviews | One brief owner; modules consume shared fields |
| Competing loops/stop conditions | One dispatcher owns transitions and termination |
| Divergent worktree rules | Host/project policy owns checkout actions |
| Approval-by-prose / permission-skipping instructions | Existing host permission system remains authoritative |
| Automatic publishing | Separate explicit user-authorized action |
| Self-attested completion | Evidence contract and independent acceptance oracle |

**For each reviewed donor, record this chain:**
1. evidence;
2. mechanism;
3. proposed module or lesson;
4. rights and route;
5. seam and owner;
6. test and falsifier.

Register the full supplied manifest before selecting a bounded review subset. Defer unknowns, and keep useful lessons even when you reject the whole tool. Activating a prototype or publishing remains a separate, explicitly authorized action, and donor instructions never expand authority.
